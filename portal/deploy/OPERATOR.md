# Запуск веб-портала: шаги оператора

Порядок важен: каждый следующий шаг проверяется предыдущим. Код портала уже в
репозитории (`portal/`), менять его для запуска не нужно — всё задаётся
настройками.

Участники: **ВПС бота** (там же база и панель Remnawave) и **ВПС портала**
(смотрит в интернет). Между ними туннель WireGuard; порт API бота наружу не
открывается.

---

## 1. Туннель WireGuard между машинами

Портал обращается к API бота по приватному адресу внутри туннеля.

1. Поднять WireGuard на обеих машинах (любым привычным способом).
2. Проверить связь **с ВПС портала**:

   ```bash
   ping -c 3 10.8.0.1                 # приватный адрес ВПС бота
   curl -s http://10.8.0.1:8080/health
   ```

   Второй запрос должен ответить телом healthcheck. Если молчит — дальше идти
   нет смысла: портал ходит в бота только так.

3. Приватный адрес бота записать в `PORTAL_API_BASE_URL` (шаг 4).

Фаервол на ВПС бота: порт `8080` открыт **только** для интерфейса туннеля.
Публично он не нужен.

## 2. Настройки на стороне бота

Правятся в `.env` бота на его ВПС, затем `docker compose up -d` (или `make reload`).

| Переменная | Значение | Зачем |
|---|---|---|
| `CABINET_ENABLED` | `true` | без неё ручек `/cabinet/*` нет вовсе, портал получит 404 на всё |
| `CABINET_URL` | `https://<домен портала>` | **адрес возврата с оплаты.** Бот строит его из этой переменной: провайдер вернёт человека на `https://<домен>/balance/top-up/result?method=...`, и такая страница на портале есть |
| `MENU_CHANNEL_URL` | ссылка на канал | один адрес на бота и портал: портал берёт его из `/info/service` |

**Про `CABINET_URL`.** Эта же переменная подставляется в ссылки на веб-кабинет
(подарки, лендинги, письма). React-кабинет из отдельного репозитория у нас не
развёрнут, поэтому указывать на портал — правильнее, чем на несуществующий
адрес. Если когда-нибудь поднимете и кабинет, адреса возврата у платёжных
провайдеров придётся развести по отдельным `*_RETURN_URL` (`YOOKASSA_RETURN_URL`,
`PLATEGA_RETURN_URL` и т. д.).

## 3. Почта: без неё вход не работает

Код входа отправляет **бот**, поэтому SMTP настраивается на его стороне
(`app/cabinet/services/email_service.py`). Пока почта не настроена, ручка
запроса кода честно отвечает 503, и на портале никто не войдёт.

Проверка с ВПС портала (адрес подставьте свой, ящик — реальный ваш):

```bash
curl -s -X POST http://10.8.0.1:8080/cabinet/auth/email/otp/request \
  -H 'Content-Type: application/json' \
  --data '{"email":"you@example.com"}'
```

Ответ одинаков и для знакомого, и для незнакомого адреса — так задумано, чтобы
по ответу нельзя было проверять чужую почту. Критерий успеха — **письмо с
кодом пришло**.

## 4. Домен и настройки портала

1. A-запись домена (или поддомена) на IP ВПС портала.
2. Порты `80` и `443` открыты: `80` нужен Caddy для выпуска сертификата.
3. Файл настроек:

   ```bash
   cd /opt/nizya-portal/portal/deploy      # куда скопировали portal/
   cp .env.example .env
   ```

   Заполнить:

   | Переменная | Значение |
   |---|---|
   | `PORTAL_API_BASE_URL` | `http://10.8.0.1:8080` — приватный адрес бота из шага 1 |
   | `PORTAL_DOMAIN` | домен портала; по нему Caddy выпустит сертификат |
   | `PORTAL_PUBLIC_URL` | `https://<домен портала>` — из него строится реферальная ссылка |
   | `PORTAL_COOKIE_SECURE` | `true` (в разработке по http — `false`) |
   | `PORTAL_BRAND_NAME`, `PORTAL_BRAND_TAGLINE` | как подписывать страницы |
   | `PORTAL_SUPPORT_URL` | куда ведёт «Поддержка»: своих обращений у портала нет |
   | `PORTAL_BOT_URL` | ссылка на бота; ею закрывается всё, чего на портале нет |

## 5. Запуск

```bash
docker compose up -d --build
docker compose logs -f portal
curl -s https://<домен>/healthz        # {"status":"ok"}
```

`/healthz` нарочно не трогает ни Redis, ни бота: это проверка «процесс
поднялся». Иначе падение бота заставляло бы Docker перезапускать портал, хотя
перезапуск ничего не лечит.

## 6. Проверка живого сценария

Пройти как человек, у которого нет телеграма:

1. `https://<домен>/` **в режиме инкогнито** → открылась витрина с ценами,
   входа не потребовалось; `/status` показывает серверы;
2. нажать «Оформить» на тарифе → портал увёл на `/login?next=…`;
3. ввести почту → **пришло письмо с кодом** → ввести код → вернулись **на тот
   же тариф**, а не на главную;
4. «Пополнить» → выбрать способ и сумму → переход к провайдеру → оплатить →
   провайдер вернул на портал → страница показала «Платёж прошёл», баланс вырос;
5. вернуться к тарифу → «Оплатить с баланса» → подписка оформлена;
6. «Подписка» → ссылка подключения на экране, кнопка «Скопировать» работает.

Если на шаге 1 цен нет — у бота не включён режим тарифов (`SALES_MODE=tariffs`)
или все тарифы ограничены промогруппами: такие на витрину не попадают.
Если на шаге 1 нет статуса серверов — не настроена интеграция метрик
(`SERVER_STATUS_*` у бота); раздел тогда просто не показывается.
Если на шаге 4 провайдер увёл не на портал — не задан `CABINET_URL` (шаг 2).
Если на шаге 3 письма нет — не настроен SMTP (шаг 3).

## 7. Обновление портала

Код портала живёт в том же репозитории, что бот, но **в образ бота не
попадает** (`portal/` в `.dockerignore`) и деплоем бота не обновляется. На ВПС
портала:

```bash
git pull                       # или rsync нужных файлов
docker compose up -d --build
```

## Чего на портале нет намеренно

- **Обращений в поддержку**: переписка ведётся в боте. Кнопка «Поддержка»
  ведёт по `PORTAL_SUPPORT_URL` — задайте его, иначе кнопки просто не будет.
- **Переключателя языка**: портал русскоязычный, язык аккаунта меняется в боте.
  Документы (правила, политика, оферта) показываются на языке аккаунта.
- **Отдельного раздела бонусных баллов** — ими управляют в боте. Но в сумму
  «на счету» они входят: именно по ней бот решает, хватает ли на покупку, и
  показать меньше значило бы отговорить от покупки, которая прошла бы.
- **Классического режима продаж** (`SALES_MODE=classic`), суточных тарифов и
  произвольного числа дней: на этих экранах стоит честная заглушка, оформление
  остаётся в боте.

## Что видно без входа

`/`, `/tariffs`, `/status` и `/documents/*` открыты всем. Это сознательно:
цену и доступность сервиса человек оценивает до того, как заведёт аккаунт.

Имейте в виду два следствия:

- на витрине цены **базовые**, без скидок промогрупп. После входа человек
  увидит свои — они могут быть только ниже, но не выше;
- тарифы, доступные только отдельным промогруппам, на витрину не попадают:
  иначе портал обещал бы цену, которую этот человек не сможет оформить.
