# Веб-портал Nizya

Витрина и личный кабинет в браузере: тарифы и статус серверов видны всем,
вход по коду из письма, покупка с баланса, устройства, промокоды, рефералка.
Отдельный сервис — живёт на своей ВПС и ходит в API бота (`app/cabinet/`)
через туннель WireGuard.

## Почему так

- **Отдельная машина.** Портал смотрит в интернет, бот — нет. Падение или
  взлом портала не роняет бота и не даёт доступа к его базе.
- **Серверный рендер.** Страницы собираются на сервере (Jinja), токены
  пользователя остаются в Redis портала, в браузер уходит только
  идентификатор сессии. Поэтому CORS не нужен вовсе: браузер в API бота не
  ходит.
- **Один набор версий.** Зависимости портала пиннятся теми же версиями, что
  в `pyproject.toml` бота: расходиться им незачем, а тесты портала гоняются
  в том же CI.

## Сначала смотрят, потом входят

Витрина (`/`, `/tariffs`, `/status`, `/documents/*`) открыта без входа:
цену и доступность сервиса человек оценивает до того, как заведёт аккаунт, и
гейт на этих страницах просто терял бы его. Почту спрашиваем в тот момент,
когда дело доходит до денег или до личных данных.

Технически это два источника одних и тех же тарифов:

- без сессии каталог берётся из `GET /cabinet/public/tariffs` — базовые цены,
  без скидок промогруппы и без отметки «ваш тариф». Тарифы, ограниченные
  промогруппами, туда не попадают: обещать цену, которую человек не сможет
  оформить, нельзя;
- после входа — из `GET /cabinet/purchase-options`, с его скидками.

Отсюда свойство, на которое можно опираться: **цена с витрины — верхняя
граница.** После входа она может только уменьшиться.

Страница, которой нужна сессия, уводит на `/login?next=<куда шёл>`, и после
входа человек возвращается ровно туда — на выбранный тариф, а не на главную
кабинета. Адрес возврата проверяется (`safe_next` в `deps.py`): принимается
только путь от корня, иначе чужая страница уводила бы человека к себе сразу
после успешного входа.

## Экраны

Публичные — без сессии:

| Путь | Что делает |
|---|---|
| `GET /` | витрина: о сервисе, цены, строка о статусе серверов |
| `GET /tariffs?days=N` | каталог; `days` выбирает срок в переключателе |
| `GET /status` | статус серверов: кто в сети и с какой задержкой |
| `GET /documents/{rules,privacy,offer}` | правила, политика, оферта |
| `GET/POST /login` | почта → письмо с кодом; `?ref=КОД` — реферальная ссылка, `?next=` — куда вернуть |
| `POST /login/code` | код → сессия (на первом входе — галочки документов) |
| `GET /healthz` | живость процесса |

После входа:

| Путь | Что делает |
|---|---|
| `GET /dashboard` | подписка: срок, трафик, устройства, ссылка подключения |
| `GET /tariffs/{id}?days=N` | подтверждение покупки, ничего не списывает |
| `POST /tariffs/{id}/buy` | списание с баланса, только с CSRF-токеном |
| `GET /balance` | баланс, история операций, незавершённые платежи |
| `GET/POST /balance/topup` | выбор способа и суммы → платёж у провайдера |
| `GET /balance/top-up/result?method=…` | возврат от провайдера (адрес строит бот) |
| `GET /balance/payment/{method}/{id}` | проверка статуса платежа |
| `GET /devices` | устройства; карточка, переименование, отключение |
| `GET /devices-reset` | отключить все устройства (с подтверждением) |
| `GET/POST /promocode` | активация промокода |
| `GET /referral` | код, ссылки, итоги, приглашённые |
| `POST /logout` | выход (CSRF) |

`/` вошедшего переводит на `/dashboard`: витрина ему больше не нужна, а свою
подписку он искал бы среди рекламных блоков.

## Внешний вид

Оформление повторяет баннеры разделов бота: глубокий тёмный фон, фиолетовый
`#7B4FC9` с лаймовым `#9CC94F`, иллюстрации Низи в шапке каждого раздела —
того же раздела, что в боте. Светлой темы нет нарочно: иллюстрации вырезаны
вместе со своим тёмным фоном, и на светлой странице вокруг каждой появился бы
прямоугольник.

Иллюстрации (`portal/static/img/mascot/*.webp`) нарезаются из баннеров бота
скриптом `portal/tools/extract_mascots.py` (нужен Pillow) и коммитятся в
репозиторий: на проде ни Pillow, ни `menu_images/` нет. Если перерисовали
баннеры — перезапустите скрипт. Цвет фона в нём (`BACKDROP`) обязан совпадать
с `--bg` в `portal/static/portal.css`.

Страница работает без JavaScript целиком: переключатель срока — это ссылки,
формы отправляются обычным POST. `portal/static/portal.js` добавляет только
то, чего без скрипта нет, — копирование в буфер и ввод кода из письма.

Политика портала (`Caddyfile`) запрещает встроенные стили и скрипты
(`style-src 'self'; script-src 'self'`). Поэтому в шаблонах нет ни одного
атрибута `style`, а то, что считается по данным, — ширина полосы трафика —
задано готовыми классами `.fill-0 … .fill-100` в `portal.css`.

Пошаговый запуск — **[OPERATOR.md](OPERATOR.md)**: туннель, настройки бота,
почта, домен, проверка живого сценария оплаты.

Деньги зачисляет бот по вебхуку от провайдера — портал в этом не участник и
«успешной оплатой» ничего не считает. На возврате он спрашивает бота о статусе
платежа, поэтому заход на страницу возврата сам по себе ничего не начисляет.

Цену на экранах покупки целиком даёт бот (`/subscription/purchase-options`):
портал её не считает и не пересчитывает. Скидки промогруппы и промо-предложения
живут на стороне бота, и посчитанная на портале цена расходилась бы со
списанием. По той же причине подтверждение — GET: его можно обновить и уйти
назад, деньги списывает только POST.

Чего портал не оформляет (на экране честная заглушка, а не половина воронки):
классический режим продаж (`SALES_MODE=classic`), суточные тарифы,
произвольное число дней и трафика, продление уже купленного тарифа в режиме
нескольких подписок и бонусные баллы. Всё это остаётся в боте; причины — в
OPERATOR.md.

Чего на портале нет сознательно: обращений в поддержку (ведутся в боте,
ссылка — `PORTAL_SUPPORT_URL`) и переключателя языка (портал русскоязычный,
язык аккаунта меняется в боте). Бонусные баллы отдельным разделом не
показываются, но входят в сумму «на счету»: именно по ней бот решает, хватает
ли на покупку, и показать меньше значило бы отговорить от покупки, которая
прошла бы.

## Что нужно поднять

Коротко: туннель WireGuard, `CABINET_ENABLED=true` и `CABINET_URL` на домен
портала у бота, рабочий SMTP у бота (без него вход по коду не работает), домен
портала в A-записи и в `PORTAL_DOMAIN`.

Пошагово, с проверками после каждого шага — **[OPERATOR.md](OPERATOR.md)**.

## Запуск

```bash
cp .env.example .env     # заполнить адреса и домен
docker compose up -d --build
docker compose logs -f portal
```

Проверка: `curl -s https://<домен>/healthz` → `{"status":"ok"}`.

`/healthz` нарочно не трогает ни Redis, ни бота: это проверка «процесс
поднялся». Иначе падение бота заставляло бы Docker перезапускать портал, хотя
перезапуск ничего не лечит.

## Файлы

| Файл | Зачем |
|---|---|
| `Dockerfile` | образ портала; контекст сборки — каталог `portal/` (в корне репозитория его прячет корневой `.dockerignore`) |
| `docker-compose.yml` | портал + его Redis + Caddy |
| `Caddyfile` | TLS, заголовки безопасности, проксирование на портал |
| `requirements.txt` | версии как у бота |
| `.env.example` | шаблон конфига |
| `OPERATOR.md` | пошаговый запуск для оператора |

## Разработка на своей машине

```bash
PORTAL_COOKIE_SECURE=false PORTAL_API_BASE_URL=http://127.0.0.1:8080 \
  uv run uvicorn portal.main:app --reload
```

`PORTAL_COOKIE_SECURE=false` нужен только тут: по http браузер cookie с
флагом `Secure` не сохранит. На проде флаг включён.

Тесты портала — в `tests/web_portal/`, гоняются общим `make test`.
